# Customer representative signatures

`reports.customer_signature` stores version 1 vector strokes, signer name/title, and explicit consent. Coordinates are bounded to a 600x240 canvas; the database validator matches `packages/validation/src/customer-signature.ts`: exact keys only, numeric `version: 1`, boolean `consent: true`, 1-40 strokes, 2-500 points per stroke, 2,000 points total, and minimum path length 30. `customer_signed_at` is assigned with database time and `customer_signed_by` is assigned from the authenticated `auth.uid()` profile only when a report is submitted with signature evidence; client-supplied provenance values are ignored.

`reports.customer_signature_required` is a report-specific rollout marker for clients that support customer representative approval. It is not a role, security, tenant, or authorization claim. Web report drafts must set it to `true`; once true on a report it cannot be cleared. During Expo rollout, legacy clients that do not set the marker may still submit unsigned reports, and those rows keep `customer_signature`, `customer_signed_at`, and `customer_signed_by` null. If the marker is true, or if any signature evidence is supplied, submission requires a valid signature.

Draft rows must keep all customer signature evidence fields null. Existing submitted rows without a signature are grandfathered and cannot receive a signature later. Once signed, the report row is immutable except `updated_at` and database-driven foreign-key `SET NULL` preservation fields. Signed report child rows reject inserts, updates, direct deletes, and attempts to move existing child rows away from the signed report so report contents remain stable after approval. Full report deletion must delete the parent `reports` row first and rely on `ON DELETE CASCADE` for child metadata cleanup; after the parent is gone, service cleanup may remove orphaned storage objects. Direct authenticated storage deletion is blocked while the signed parent report exists. For drafts, the storage policy also permits the report creator or an organization owner/admin to clean an object after its metadata row has been removed. Database-driven `SET NULL` cleanup on child profile references is allowed only when the child snapshot itself stays unchanged.

Deploy the migration before releasing web code that writes `customer_signature_required`. Keep the marker-based compatibility boundary until Expo also sends signature payloads.
